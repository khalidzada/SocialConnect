# SocialConnect — Domain Model & Engineering Architecture Contract

**Document Status:** Canonical / Architecture Contract
**Project:** SocialConnect
**Platform:** ASP.NET Core MVC / .NET 8
**Architecture:** Layered Modular Monolith
**ORM:** Entity Framework Core
**Database:** SQL Server

---

## 1. Purpose

This document defines the canonical domain-model structure and the engineering architecture that governs SocialConnect.

It establishes:

* the domain entity hierarchy;
* the distinction between Identity and domain entities;
* the responsibilities of `BaseEntity`, `AuditableEntity`, `SoftDeleteEntity`, and `Reactable`;
* the `TargetType + TargetId` cross-domain targeting mechanism;
* domain ownership boundaries;
* repository and Unit of Work responsibilities;
* application/service boundaries;
* MVC/ViewModel/ViewComponent architecture;
* event, notification, media, marketplace, and administration integration boundaries;
* the rules that must be followed when existing modules are investigated or new modules are implemented.

This document is a **contract**, not merely a description of the current codebase.

Existing implementation must therefore be evaluated against this contract. Existing code is evidence of the current implementation; it does not automatically redefine the architectural contract.

---

# 2. Architectural Foundation

SocialConnect is a **layered modular monolith**.

It is one ASP.NET Core MVC application with clearly separated architectural responsibilities.

The system is intentionally **not** designed as a collection of microservices.

The principal architectural direction is:

```text
Presentation
    ↓
Application
    ↓
Domain
    ↓
Infrastructure
    ↓
Framework / Database
```

With cross-cutting infrastructure such as:

```text
Identity
Persistence
Events
Outbox
Notifications
Media
Logging
Configuration
```

implemented without allowing those concerns to destroy domain ownership.

The architecture favors:

* explicit contracts;
* loose coupling;
* small focused services;
* orchestration over God services;
* server-owned business rules;
* reusable UI components;
* explicit domain ownership;
* transactional consistency;
* predictable persistence behavior.

# 3. Domain Model Philosophy

The SocialConnect domain model is based on a **shared entity hierarchy**.

The hierarchy provides common persistence and lifecycle capabilities without forcing unrelated business entities into one large inheritance structure.

The canonical hierarchy is:

```text
BaseEntity
    │
    └── AuditableEntity
            │
            └── SoftDeleteEntity
                    │
                    └── Reactable
```

Not every domain entity must derive from `Reactable`.

The hierarchy is therefore capability-oriented:

```text
BaseEntity
    ├── entities requiring only identity
    │
    └── AuditableEntity
            ├── entities requiring audit
            │
            └── SoftDeleteEntity
                    ├── entities requiring soft deletion
                    │
                    └── Reactable
                            └── entities supporting reactions
```

This distinction is important.

Inheritance represents **shared domain/persistence capability**.

It does **not** represent business relationships between entities.

For example:

```text
Post
Comment
Product
Shop
```

may participate in relationships with one another, but that does not mean they should inherit from one another.

# 4. Domain Entity Hierarchy

## 4.1 BaseEntity

`BaseEntity` is the foundational base class for SocialConnect domain entities.

Canonical responsibility:

```csharp
public abstract class BaseEntity
{
    public Guid Id { get; set; } = Guid.NewGuid();
}
```

### Responsibilities

`BaseEntity` provides:

* the primary domain identifier;
* a consistent identifier type;
* a common entity root for domain entities.

The canonical identifier type is:

```text
Guid
```

The identifier is generated by default when an entity instance is created.

Example:

```text
9B0F3E8C-7F64-4C62-B8D1-3E5E7A8B2D61
```

### Architectural rule

`BaseEntity` contains **identity only**.

It must not accumulate:

* audit logic;
* business-specific properties;
* UI properties;
* repository dependencies;
* service dependencies;
* HTTP concerns;
* notification concerns.

---

# 5. AuditableEntity

`AuditableEntity` extends `BaseEntity`.

```text
BaseEntity
    ↓
AuditableEntity
```

It introduces creation and modification auditing.

Canonical properties:

```csharp
public abstract class AuditableEntity : BaseEntity
{
    public DateTime CreatedAt { get; set; } = DateTime.UtcNow;

    public string? CreatedBy { get; set; }

    public DateTime? UpdatedAt { get; set; }

    public string? UpdatedBy { get; set; }
}
```

## 5.1 CreatedAt

Records the UTC date/time when the entity was created.

Canonical rule:

```text
All timestamps are stored in UTC.
```

## 5.2 CreatedBy

Contains the identifier of the user responsible for creating the record.

Conceptually:

```text
CreatedBy → ApplicationUser.Id
```

It is nullable because some records may be generated by the system rather than directly by a user.

## 5.3 UpdatedAt

Records the UTC date/time of the most recent modification.

## 5.4 UpdatedBy

Contains the user identifier responsible for the most recent modification.

It represents:

```text
UpdatedBy → ApplicationUser.Id
```

---

# 6. SoftDeleteEntity

`SoftDeleteEntity` extends `AuditableEntity`.

```text
BaseEntity
    ↓
AuditableEntity
    ↓
SoftDeleteEntity
```

It introduces the standard SocialConnect soft-delete lifecycle.

Canonical properties:

```csharp
public abstract class SoftDeleteEntity : AuditableEntity
{
    public bool IsDeleted { get; set; } = false;

    public DateTime? DeletedAt { get; set; }

    public string? DeletedBy { get; set; }
}
```

## 6.1 IsDeleted

Indicates whether the entity has been logically deleted.

```text
false → active
true  → deleted
```

## 6.2 DeletedAt

Records the UTC time at which the entity was logically deleted.

```text
null → not deleted
value → deleted
```

## 6.3 DeletedBy

Records the user responsible for the deletion.

Conceptually:

```text
DeletedBy → ApplicationUser.Id
```

System-generated deletion may result in a null value where appropriate.

---

# 7. Soft Deletion Contract

Soft deletion is a domain persistence capability.

A soft-deleted entity normally remains physically present in the database.

The normal application read path must therefore respect:

```text
IsDeleted == false
```

unless an explicit administrative, auditing, recovery, or diagnostic operation requires deleted records.

Soft deletion must not be confused with account deactivation.

For example:

```text
User account deactivation
≠
Domain entity soft deletion
```

These represent different business concepts.

---

# 8. Reactable

`Reactable` extends `SoftDeleteEntity`.

```text
BaseEntity
    ↓
AuditableEntity
    ↓
SoftDeleteEntity
    ↓
Reactable
```

`Reactable` is the shared domain capability for entities that support SocialConnect reactions.

Canonical structure:

```csharp
public abstract class Reactable : SoftDeleteEntity
{
    public int TotalReactionsCount { get; set; }

    public ReactionAggregate ReactionAggregate { get; set; } = new();
}
```

---

# 9. ReactionAggregate

`ReactionAggregate` stores reaction counters associated with a `Reactable` entity.

Canonical reaction types are:

```text
Like
Love
Haha
Wow
Sad
Angry
```

The aggregate contains:

```csharp
public class ReactionAggregate
{
    public int LikeCount { get; set; }

    public int LoveCount { get; set; }

    public int HahaCount { get; set; }

    public int WowCount { get; set; }

    public int SadCount { get; set; }

    public int AngryCount { get; set; }
}
```

It therefore provides:

```text
TotalReactionsCount
    +
LikeCount
LoveCount
HahaCount
WowCount
SadCount
AngryCount
```

---

# 10. Reactable Does Not Own Reaction Records

`Reactable` owns the **aggregate reaction state**.

It does not mean that the entity owns the `Reaction` persistence workflow.

The distinction is:

```text
Reactable
    ↓
reaction aggregate / counters
```

while:

```text
Reaction
    ↓
individual user's reaction record
```

The Reaction domain/application services remain responsible for:

* validating reaction operations;
* enforcing reaction rules;
* creating/removing/updating individual reactions;
* maintaining aggregate counters;
* raising appropriate domain/integration events where applicable.

The reusable reaction UI must not manipulate `Reactable` internals directly.

---

# 11. View Analytics Are Not Part of Reactable

The current domain contract intentionally does not place view analytics inside `Reactable`.

The following properties remain excluded:

```csharp
// public long TotalViewCount { get; set; }
// public long UniqueViewCount { get; set; }
```

Therefore:

```text
Reaction capability
≠
View analytics capability
```

If view tracking is introduced later, it must be evaluated as its own domain capability rather than being added casually to `Reactable`.

---

# 12. ApplicationUser Is Outside the Domain Entity Hierarchy

This is a critical architectural distinction.

`ApplicationUser` is an ASP.NET Core Identity entity.

It does **not** belong underneath:

```text
BaseEntity
    ↓
AuditableEntity
    ↓
SoftDeleteEntity
    ↓
Reactable
```

The relationship is instead:

```text
                    Identity / Account Boundary
                              │
                              ▼
                       ApplicationUser
                              │
                              │ references identity
                              ▼
                     SocialConnect Domain
                              │
                 ┌────────────┴────────────┐
                 ▼                         ▼
             UserProfile             Domain Entities
                                           │
                                           ▼
                                      BaseEntity
```

This separation is intentional.

`ApplicationUser` exists to support:

* ASP.NET Core Identity;
* authentication;
* credential management;
* external authentication;
* roles;
* account security;
* security-related user state.

SocialConnect business entities derive from the domain hierarchy independently.

# 13. ApplicationUser Responsibilities

`ApplicationUser` represents the authenticated Identity account.

Its responsibilities include Identity/account concerns such as:

* authentication identity;
* login credentials;
* email/phone identity information;
* account activation state;
* verification state;
* registration information;
* last-login information;
* Identity relationships;
* relationship to the business `UserProfile`.

The current structure includes:

```csharp
public class ApplicationUser : IdentityUser
{
    public string FirstName { get; set; } = string.Empty;

    public string LastName { get; set; } = string.Empty;

    [NotMapped]
    public string FullName => $"{FirstName} {LastName}";

    public bool IsActive { get; set; } = true;

    public bool IsVerified { get; set; } = false;

    public DateTime RegisteredAt { get; set; } = DateTime.UtcNow;

    public DateTime? LastLoginAt { get; set; }

    public virtual UserProfile? Profile { get; set; }
}
```

The remaining navigation collections represent relationships between the Identity account and SocialConnect business entities.

They do not change the architectural distinction between Identity and the domain hierarchy.

---

# 14. ApplicationUser vs UserProfile

The separation is mandatory.

```text
ApplicationUser
    =
Identity/account/security identity

UserProfile
    =
SocialConnect business/profile information
```

`ApplicationUser` must not become a general-purpose business entity.

Business profile information belongs in `UserProfile`.

The intended relationship is:

```text
ApplicationUser
      │
      │ 1 : 1
      ▼
UserProfile
```

The first successful authentication/registration flow must ensure that an appropriate `UserProfile` exists.

The initial profile may be empty.

The user can subsequently complete or update profile information.

# 15. External Authentication

The account architecture must support external authentication providers including:

```text
Facebook
Google
```

The external authentication flow must ultimately establish or link the SocialConnect `ApplicationUser`.

The Identity boundary owns authentication.

The domain/application layer owns the business consequences of creating or updating the SocialConnect user/profile state.

The external provider must not become a business-domain dependency.

# 16. User Account Security

The account system must support the user's own security-management responsibilities, subject to the final Identity/security implementation contract.

This includes:

* credential management;
* credential activation/deactivation where supported by the account model;
* two-factor authentication;
* email verification;
* account security state;
* account deletion/deactivation workflows.

Security operations must not be implemented by directly manipulating Identity tables from MVC controllers.

---

# 17. Administrative Account Constraints

The canonical administrative roles are:

```text
Admin
Moderator
Vendor
User
```

There is no V1 `SuperAdmin` role.

Buyer/seller behavior is treated as a capability/business role rather than requiring separate user entity classes.

Administrative users are subject to additional governance constraints.

In particular:

```text
Admin/Moderator
    ≠
ordinary self-service account deletion
```

The final account-governance implementation must prevent Admin and Moderator accounts from deleting themselves through the normal user deletion workflow.

---

# 18. Email Verification

Email verification is part of account security and account policy.

The final account implementation must enforce the configured verification policy rather than assuming that an authenticated Identity record automatically represents a fully verified SocialConnect account.

The distinction is:

```text
authenticated
≠
email verified
≠
platform verified
```

Where each state has its own defined meaning.

Typical examples include:

```text
Post
```

# 20. Domain Ownership

Every business operation must have a clear owner.

The ownership rule is:

> The domain/application service responsible for a business concept owns its business rules and workflow.

Examples:

```text
Post creation
    → Post Creation workflow

Comment creation
    → Comment workflow

Reaction toggle
    → Reaction workflow

Media upload
    → Media upload workflow

Notification persistence
    → Notification workflow

Administration mutation
    → Administration workflow
    → appropriate domain/application operation
```

Controllers must not become business-operation owners.

# 21. TargetType + TargetId

`TargetType + TargetId` is a fundamental SocialConnect cross-domain reference mechanism.

It is **not inheritance**.

It is **not a replacement for foreign keys where a normal relationship exists**.

It is a polymorphic targeting contract used where a feature must operate against different domain entity types.

Canonical concept:

```text
TargetType
TargetId
```

Example:

```text
TargetType = Post
TargetId   = <Post Guid>
```

or:

```text
TargetType = Comment
TargetId   = <Comment Guid>
```

or:

```text
TargetType = Product
TargetId   = <Product Guid>
```

---

# 22. Why TargetType + TargetId Exists

Several SocialConnect subsystems need to target different kinds of domain entities.

Examples include:

```text
Reaction
Comment
Notification
Event
Reporting
Moderation
Media ownership
Future analytics
```

Instead of creating separate structural models for every possible target, these subsystems can use the shared targeting contract.

Conceptually:

```text
Feature
   │
   ├── TargetType
   │
   └── TargetId
          │
          ▼
    Target Resolver
          │
    ┌─────┼─────┬─────┐
    ▼     ▼     ▼     ▼
   Post Comment Product Shop ...
```

---

# 23. TargetType Is a Domain Contract

`TargetType` identifies **what kind of entity** is being targeted.

It must have a canonical definition.

The system must not allow arbitrary strings to become uncontrolled target types.

A target type must correspond to a known SocialConnect domain concept.

The exact enum/constants registry must remain aligned with the canonical domain contract.

---

# 24. TargetId Is the Entity Identifier

`TargetId` identifies the concrete entity instance.

For SocialConnect domain entities, this normally corresponds to:

```text
BaseEntity.Id
```

Therefore:

```text
TargetType = Post
TargetId   = Post.Id
```

The target identifier does not itself provide enough information to resolve the entity.

Both values are required:

```text
TargetType + TargetId
```

---

# 25. Target Resolution

Target resolution must be explicit.

The application must resolve:

```text
TargetType + TargetId
        ↓
correct domain entity
        ↓
entity owner / required business context
```

This is particularly important for notification recipient resolution.

For example:

```text
TargetType + TargetId
        ↓
TargetOwnerSource
        ↓
resolve correct target entity
        ↓
determine target owner
```

Target resolution must not become a giant `switch` inside unrelated business services.

Where multiple target types are supported, dedicated resolver/source abstractions should be used.

---

# 26. TargetType Is Not a Generic Repository Shortcut

The existence of `TargetType + TargetId` does not mean that the application should bypass normal domain ownership and query arbitrary tables.

This is prohibited:

```text
TargetType
   ↓
direct table manipulation
```

Instead:

```text
TargetType + TargetId
   ↓
resolver/loader
   ↓
appropriate domain/application boundary
```

The target mechanism provides identification.

It does not grant permission to bypass architecture.

---

# 27. TargetType + TargetId and Foreign Keys

The two mechanisms serve different purposes.

### Normal relationship

Use a normal foreign key where the domain relationship is structurally known.

Example:

```text
Comment
    ParentCommentId
```

or:

```text
Shop
    OwnerId
```

### Polymorphic target

Use:

```text
TargetType + TargetId
```

when one feature legitimately targets multiple entity types.

Therefore:

```text
Known relationship
    → FK/navigation

Polymorphic target
    → TargetType + TargetId
```

The system must not replace every foreign key with a polymorphic target merely for convenience.

---

# 28. Repository Architecture

Repositories are persistence abstractions.

The canonical direction is:

```text
Application Service
        ↓
Loader / Lookup / Repository abstraction
        ↓
Persistence
```

Business services must not become tightly coupled to raw persistence implementation.

---

# 29. Generic Repository

The Generic Repository provides common persistence operations shared across domain entities.

Its responsibility is persistence abstraction, not business logic.

It must not contain:

* notification rules;
* authorization policy;
* moderation policy;
* post-creation workflows;
* media finalization logic;
* business orchestration;
* UI mapping.

Generic repository query operations should normally respect the project's tracking conventions.

The established convention is:

```text
Query / GetById
    → no-tracking where appropriate

ForUpdate
    → tracked
```

The exact implementation must be verified during repository investigation.

---

# 30. Specialized User Repository

`ApplicationUser` is outside the SocialConnect `BaseEntity` hierarchy and is an ASP.NET Identity entity.

Therefore, its repository is necessarily specialized.

The specialized User Repository exists to encapsulate Identity/user persistence and user-specific discovery requirements.

It must not become a general business-service container.

The current repository implementation will therefore be investigated for separation of:

```text
Identity access
User persistence
User discovery
Pagination
DTO projection
Business orchestration
```

Only the appropriate persistence/query responsibilities belong inside the repository.

---

# 31. Repository vs Loader vs Lookup Service

SocialConnect distinguishes persistence from application-level retrieval.

The architecture uses loader abstractions such as:

```csharp
IEntityLoader<TEntity, TKey>
ITrackedEntityLoader<TEntity, TKey>
```

These provide controlled retrieval to application/business services.

A lookup service may act as a public read gateway where a domain concept requires reusable query behavior.

The responsibility boundary is:

```text
Repository
    → persistence

Loader
    → controlled entity retrieval

Lookup Service
    → reusable application-level read gateway

Application Service
    → business operation/orchestration
```

This prevents repositories from becoming God classes.

---

# 32. DTOs

DTOs are service/application transport contracts.

They are not domain entities.

They must not become persistence models.

They are used where an application/service boundary requires a stable data contract.

Example:

```text
CreatePostDto
UserSummaryDto
```

DTO mapping is manual.

The project does not use AutoMapper.

---

# 33. ViewModels

ViewModels belong to the presentation layer.

They are not domain entities.

They exist to provide exactly the state required by a Razor View or ViewComponent.

The canonical direction is:

```text
Domain/Application State
        ↓
Builder / Resolver / Orchestrator
        ↓
ViewModel
        ↓
Razor
```

A ViewModel must not become a persistence object.

---

# 34. MVVM-in-MVC

SocialConnect uses an MVVM-oriented presentation structure within ASP.NET Core MVC.

The responsibilities are:

```text
Controller
    → HTTP boundary

Application Service
    → business operation

Builder / Resolver
    → construct presentation state

ViewModel
    → presentation state

Razor View
    → render

JavaScript
    → interaction
```

---

# 35. Thin Controllers

MVC controllers must remain thin.

A controller should:

1. receive the request;
2. invoke the appropriate application service;
3. handle the result;
4. return the appropriate View/API response.

Controllers must not contain:

* business workflows;
* repository queries;
* notification orchestration;
* media workflows;
* complex mapping;
* authorization logic beyond the established boundary;
* transaction orchestration unless explicitly defined by the application contract.

---

# 36. Standard MVC Views

SocialConnect uses standard MVC Views as page shells.

A page may contain:

```text
Page View
    ├── ViewComponent
    ├── ViewComponent
    ├── Partial View
    └── TagHelpers
```

The page shell should not absorb the implementation responsibilities of reusable components.

# 37. Reusable ViewComponents

Reusable UI is implemented using the established component architecture:

```text
    ↓

    ↓

    ↓
Default.cshtml
    ↓
```

# 38. Reusable Component Golden Rule

The canonical rule is:

> A reusable component owns everything within its domain. Consumers configure it, call its public API, subscribe to its events, and react to its results. Consumers never implement or control the component's internal behaviour.

Therefore:

```text
Consumer
    ↓
configuration / public API / events
    ↓
Reusable Component
    ↓
component-owned behavior
```

Consumers must not manipulate component internals.

# 42. Unit of Work

The Unit of Work represents the persistence transaction boundary around the shared `ApplicationDbContext`.

Its responsibilities include:

* coordinating repositories;
* exposing the specialized user repository;
* saving changes;
* managing explicit database transactions where required;
* executing approved persistence-level SQL operations where explicitly supported.

The current architectural structure includes:

```text
ApplicationDbContext
       │
       ├── Generic Repositories
       │
       └── Specialized User Repository
       
UnitOfWork
       │
       └── transaction / SaveChanges coordination
```

The Unit of Work does not own business workflows.

---

# 43. Unit of Work and Transactions

Transactions are used when multiple persistence operations must succeed or fail together.

Canonical concept:

```text
Begin Transaction
    ↓
Business/Application Operation
    ↓
multiple persistence changes
    ↓
SaveChanges
    ↓
Commit
```

If the operation fails:

```text
Rollback
```

Transactional boundaries must be determined by the application workflow.

They must not be scattered randomly throughout repositories.

---

# 44. Events and Transactional Outbox

SocialConnect uses a transactional outbox architecture.

The conceptual flow is:

```text
Business Operation
    ↓
Event Raised
    ↓
Transactional Outbox Persistence
    ↓
Database Commit
    ↓
Outbox Dispatcher
    ↓
Event Handler
    ↓
Recipient Resolution
    ↓
Notification Orchestration
    ↓
Persistence / Delivery Planning
```

Domain Events and Integration Events/Outbox Events are distinct concepts.

The outbox provides durable event delivery across the application boundary.

---

# 45. Event and Notification Ownership

The event/notification platform is shared infrastructure.

Individual business modules own their business events.

For example:

```text
Post operation
    → Post event

Comment operation
    → Comment event

Reaction operation
    → Reaction event

Marketplace operation
    → Marketplace event
```

The generic event/notification infrastructure must not contain a giant hard-coded switch containing every business condition.

Operational sources plug into the stable event/notification infrastructure through explicit contracts.

---

# 46. Notification Persistence

Notification persistence is the source of truth for user notifications.

Real-time delivery mechanisms such as SignalR are delivery accelerators, not the source of truth.

Therefore:

```text
Notification persistence
    = authoritative state

SignalR
    = real-time delivery
```

A user must not lose notification state merely because real-time delivery is unavailable.

---

# 47. Media Domain Boundary

Media is a separate reusable domain capability.

The canonical flow is:

```text

    ↓

    ↓
MediaUploadService
    ↓
temporary storage
    ↓
MediaDomain
    ↓
MediaIds
    ↓
```

Finalization and assignment remain separate responsibilities.

```text

    → temp → final

Assignment
```

# 48. Administration Boundary

Administration is a privileged subsystem within the same application.

It is not a separate application.

ASP.NET Core Areas are not used for Administration.

The administrative architecture follows:

```text
Admin/Moderator
    ↓
Admin UI
    ↓
HTTP Request
    ↓
Authorization
    ↓
Validation
    ↓
Admin Application Service
    ↓
Appropriate Domain/Application Service
    ↓
Transaction
    ├── State Change
    ├── Audit
    └── Event + Outbox where applicable
    ↓
Commit
```

Administrators must not directly manipulate domain tables when a domain/application operation exists.

---

# 49. Domain Ownership Golden Rule

The central domain ownership rule is:

> An administrative or technical subsystem must not bypass the owner of a business domain merely because it has database access.

For example:

```text
Administration
    → does not directly update Post rows
    → invokes the appropriate Post/application operation

Administration
    → does not directly manipulate Reaction rows
    → invokes the appropriate Reaction operation

Administration
    → does not directly manipulate Media rows
    → invokes the appropriate Media operation
```

This protects business invariants.

Dependency injection must preserve module boundaries.

The application should prefer:



# 58. Performance and Loose Coupling

The architecture intentionally favors loose coupling because SocialConnect contains multiple interacting domains.

The design must avoid:

* unnecessary eager loading;
* large object graphs;
* unnecessary tracking;
* duplicate queries;
* God services;
* repository abuse;
* feature logic in shared infrastructure;
* excessive client-side state;
* unnecessary cross-module dependencies.

Performance improvements must not violate ownership boundaries.

# 59. Domain Model vs Database Model

The database schema represents persistence.

The domain model represents business concepts and capabilities.

They are related but not identical.

Therefore:

```text
Database convenience
    ≠
domain design authority
```

EF Core configuration may shape persistence without forcing unrelated business responsibilities into an entity.

# 69. Final Architectural Principle

The SocialConnect architecture is built around a simple separation:

```text
Identity
    → Who is the user?

Domain Model
    → What business entities exist?

Entity Hierarchy
    → What shared capabilities does an entity have?

Relationships
    → How are domain entities connected?

TargetType + TargetId
    → Which entity is a cross-domain operation targeting?

Application Services
    → What business operation is being performed?

Repositories / Loaders
    → How is persistence state retrieved or changed?

Unit of Work
    → How are persistence changes coordinated transactionally?

Events / Outbox
    → What happened and how is it reliably propagated?

Notifications
    → Who should be informed?

ViewModels / Builders
    → What state should the UI receive?

ViewComponents / Razor / JavaScript
    → How is that state presented and interacted with?
```

The architecture must preserve these boundaries as SocialConnect grows.

The objective is not merely to make the current code compile.

The objective is to maintain a domain model and application architecture in which:

```text
business ownership
        +
clear entity hierarchy
        +
explicit targeting
        +
controlled persistence
        +
transactional consistency
        +
reusable presentation
        +
loose coupling
```

remain understandable and maintainable as additional SocialConnect modules are introduced.
